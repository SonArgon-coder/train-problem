Evaluation Brief for Antigravity
Grade my project against the problem statement. Be the harshest, fairest examiner I will ever face.
1. Your Role
Antigravity, you are now the strictest, most demanding professor in the department. I was given the problem statement summarised in Section 2 and I have built a solution to it. The project is in the current workspace.
Your job is to evaluate what I actually built, requirement by requirement, and give it the score it truly deserves. Every single thing the problem statement asks for must be scored individually. I do not want comfort, encouragement, or diplomacy. I want pure justice: nothing inflated, nothing invented, nothing skipped.
2. The Problem Statement, in Brief
Title: AI-Powered Intelligent Railway Travel & Autonomous AI Governance Platform (Indian Railways).
Challenge: Build a platform that delivers predictive, personalised, and secure railway services to passengers, and an Agentic AI-powered governance layer that continuously monitors, governs, optimises, secures, and audits every AI model behind those services across its whole lifecycle.
Structure: seven passenger-facing AI modules (Modules 1–7), one centralised autonomous "AI-for-AI" governance platform (Module 8), five non-functional requirement areas, and an expected outcome of one unified ecosystem where passenger AI and governance agents work together. The full checklist to score is in Section 6.
3. Ground Rules (Non-Negotiable)
No buttering. No praise used to cushion criticism. No "great effort", no "impressive for a student", no "overall a solid foundation". State what is missing and what is broken.
Evidence or it does not count. Every score must cite a file path, function, line, or the actual output of running the code. If you cannot find evidence, the score is 0.
Claims are not proof. README text, comments, slide wording, UI labels, and function names are claims. Verify by reading the code and running it.
Fake AI is worth almost nothing. Hardcoded values, random numbers, lookup tables, or static mock data presented as AI predictions score 1 at most, and you must call it out as fake.
Planned is not built. TODOs, "future scope", and empty stubs score 0.
Score every line item. Do not merge items, skip items, or let a strong item hide a weak one. If something cannot be verified, write "Not verifiable" and score it 0 with the reason.
Be harsh, but be correct. If something is genuinely excellent, give full marks and say so in one factual sentence. Do not manufacture flaws to sound tough. Score what is there: no more, no less.
Judge against the problem statement, not against other student projects. The standard is what the statement demands, as an external examiner would read it.
When torn between two scores because the evidence is ambiguous, take the lower one. When the evidence is clear, give exactly what it earns.
Read-only. Do not edit, fix, or improve my code during evaluation. You may run it, test it, and inject test inputs.
4. How to Inspect the Project
Map the whole repository first: list every module, service, notebook, model file, dataset, config, and test.
Read the README and any documentation, then treat every claim in it as something to be verified.
Run the application, tests, and notebooks. Note anything that fails to start, crashes, or only works with manual intervention.
Inspect the models: Is a model actually trained? On what data (real, public, or synthetic)? Which metrics, on which split? Are there saved artifacts? Does it beat a naive baseline?
Inspect the agents: Do they make real tool calls and LLM calls, or is the logic scripted? Is there an audit trail of what they decided and why?
Inspect the governance layer: Does it monitor the real models from Modules 1–7, or is it a standalone dashboard showing made-up numbers?
Look for evidence of the non-functional requirements: containers, queues, caching, authentication, role-based access, logging, backups or failover, load-test results, latency measurements.
Declare any synthetic or simulated data clearly in your report. Synthetic data is acceptable only if disclosed and realistic. Presenting synthetic data as real is misrepresentation and must be flagged.

A governance or monitoring feature that is a static chart or uses made-up numbers: maximum 1.

A prediction trained on synthetic data with no realism justification: maximum 3.
Data claimed as real but actually synthetic: 0 for that item, and list it under misleading claims.

6. What Must Be Scored
Each bullet below is one line item scored 0 to 5. The "Hard test" under each module is how you should verify it. Do not take my word for anything.
Part A: Passenger-Facing AI Modules (8% each)
Module 1. Intelligent Ticket Confirmation Predictor
Predict confirmation probability for Waiting List (WL) and RAC tickets.
Estimate final berth allocation status.
Analyse historical booking and cancellation trends.
Provide confidence scores and prediction explainability.
Continuously monitor prediction accuracy, and automatically retrain when performance degrades.
Hard test: Submit a WL and an RAC scenario. Check for a probability, berth status, confidence score, and explanation. Confirm accuracy is measured on held-out data, not training data.
Module 2. Smart Train Recommendation Engine
Recommendation uses all seven factors: budget, journey duration, seat and berth availability, travel class, historical travel behaviour, train punctuality, passenger preferences. Score how many genuinely influence the output.
Monitors recommendation relevance and accuracy.
Detects recommendation bias.
Explains the rationale behind each recommendation.
Continuously optimises the recommendation models.
Hard test: Run two very different passenger profiles. Outputs must differ for sensible reasons, and each must come with a rationale. Check for bias across fare or class segments.
Module 3. Train Delay and Disruption Prediction
Predict arrival and departure delays.
Estimate station congestion levels.
Provide proactive travel alerts.
Recommend alternative travel options.
Generate confidence scores and explainability reports.
Detect model drift.

Hard test: Compare the model to a naive baseline such as historical average delay. If it does not beat the baseline, say so. Check whether the data is live or static.
